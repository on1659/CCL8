# 멀티플레이 릴레이 배포·운영 (v0.10, 2026-08-12)

> goal: `docs/goal/chicken-heist-multiplayer.md` (패널 결정 D23·D24·D31)
> 게임 페이지는 지금처럼 GitHub Pages. **릴레이 서버만** 따로 무료 티어에 올린다.

## 구조 한 장

```
친구 브라우저 ──wss──┐
친구 브라우저 ──wss──┤   릴레이 (server.js — 방 코드 + 중계만)
친구 브라우저 ──wss──┤
호스트 브라우저 ─wss──┘   ← 게임 시뮬레이션은 전부 여기서 돈다 (호스트 권위)
```

- 릴레이는 **판정하지 않는다**. 방 코드 발급 + 호스트↔클라 메시지 중계가 전부.
- 게임 페이지(chicken-heist.html)는 정적 파일 — Pages 그대로.

## 로컬 실행 (개발·같은 PC 2탭 시험)

```bash
npm install
node server.js
```

- 기본 포트 8787. 페이지를 `file://` 또는 `http://localhost`로 열면 `ws://localhost:8787`에 자동 연결.
- 타이틀의 **[친구와 함께]** → 링크 복사 → 다른 탭/브라우저에서 열면 참가.

## 공개 배포 — 현재 상태 (2026-08-12 배포 완료)

릴레이는 **Railway에 올라가 있고 살아 있다.**

- 프로젝트: `ccl8-relay` (Railway, 워크스페이스 "Young-tae. Kim's Projects")
- 릴레이 주소: **`wss://ccl8.up.railway.app`**
- 호스트가 여는 링크:
  `https://on1659.github.io/CCL8/chicken-heist.html?ws=wss://ccl8.up.railway.app`
  → [친구와 함께] → 생성된 링크(`?room=코드&ws=…` 포함)를 친구에게 보낸다. **친구는 클릭 1번.**

배포 검증(2026-08-12): 방 생성 `created` → 참가 `joined`/`peer` → 호스트 `cast` → 클라 수신까지
wss 왕복 1.2초 안에 전부 통과.

### 다시 배포할 때 (server.js를 고쳤을 때)

**보통은 아무것도 안 해도 된다 — `git push`가 곧 릴레이 배포다.** (2026-08-13 확인)

Railway 서비스가 GitHub 저장소 `on1659/CCL8`의 `main`에 연결돼 있어서, 푸시하면 릴레이가
자동으로 다시 빌드된다. 게임(Pages)과 릴레이(Railway)가 **같은 푸시 한 번에 같이 나간다.**

- 그래서 `server.js`를 건드린 커밋을 푸시하면 **의도와 무관하게 프로덕션 릴레이가 재시작된다.**
  진행 중인 방은 그때 끊긴다 — 친구들과 붙어 있는 중이면 푸시 타이밍을 고를 것.
- 반대로 `chicken-heist.html`만 고친 푸시도 릴레이를 재빌드하지만, 중계 코드가 같으므로
  결과는 무해한 재시작이다.
- 배포 상태 확인: `railway status --json`의 `latestDeployment.status`
  (`WAITING`→`BUILDING`→`SUCCESS`). JSON 안에 과거 배포도 같이 들어 있으니
  **첫 `"status"` 문자열을 grep하면 엉뚱한 걸 읽는다** — `latestDeployment`를 짚어서 볼 것.

수동 배포가 필요할 때(저장소에 안 올린 변경을 급히 올릴 때)만:

```bash
railway up --ci
```

- 저장소 루트(`D:\Work\vibe\CCL8`)에서 실행한다. 링크 정보는 저장소가 아니라 **CLI 전역 설정에
  이 폴더 경로로** 저장돼 있다 — 다른 PC에서는 `railway link -p ccl8-relay`부터 해야 한다.
- 빌드는 railpack이 `package.json`을 보고 자동 — 시작 명령은 `npm start` (`node server.js`).
- 포트는 플랫폼이 주는 `PORT` 환경변수를 그대로 읽는다 (코드 반영됨).
- 도메인은 서비스당 1개로 이미 발급됨 — 재배포해도 주소는 그대로다.
- **대시보드에서 도메인 이름을 바꾸면 이전 주소는 즉시 죽는다.** 2026-08-12에
  `ccl8-relay-production` → `ccl8`로 한 번 바꿨다. 바꿨으면 이 문서의 `?ws=` 링크와
  친구에게 이미 보낸 링크를 전부 갈아끼워야 한다.

### 다른 플랫폼으로 옮긴다면

Render/Fly 등도 조건은 같다: 시작 명령 `npm start`, `PORT` 환경변수, 기본 도메인이면 **wss 자동**.
주소가 바뀌면 위의 `?ws=` 링크만 새 도메인으로 갈아끼우면 된다.

### 브라우저로 릴레이 주소를 직접 열면 안내문이 뜬다

`https://ccl8.up.railway.app`을 주소창에 치면 "릴레이 정상 작동 중" 안내와 게임 링크가 나온다.
릴레이 주소는 주소창에 치는 게 아니라 **게임 링크의 `?ws=`에 넣는 값**이라는 걸 알려주는
텍스트 한 줄이다 — 파일 서빙도 게임 판정도 아니다 (중계 전용 원칙 유지).

원래는 여기서 `426 Upgrade Required` 한 줄만 나왔다. 규격대로면 맞는 응답이고(Upgrade는 결제가
아니라 HTTP→WebSocket 프로토콜 업그레이드다) 서버가 살아 있다는 뜻이었지만, 열어볼 때마다
고장으로 오해받아서 `http.createServer`를 앞에 두고 안내문으로 바꿨다.

→ 그러므로 **안내문이 보이면 릴레이는 정상이다.** 426이 보인다면 그건 이 안내문 커밋 이전
버전이 돌고 있다는 뜻이니 `railway up --ci`로 재배포하면 된다.

## 반드시 알아야 하는 운영 사실 (D24·D31)

- **https 페이지 + `ws://`(비암호) 주소는 브라우저가 차단한다.** 게임이 연결 시도 전에 화면에
  에러를 띄우도록 되어 있다. Pages에서는 반드시 `wss://`.
- **Railway는 기본적으로 잠들지 않는다** (App Sleeping은 옵트인). 그래서 Render류의 콜드 스타트
  30~60초는 지금 경로엔 없다 — 첫 연결도 1초 안에 붙는다. 게임의 "서버 깨우는 중…" 문구는
  다른 플랫폼으로 옮길 때를 대비한 안전망으로 남아 있는 것이지, 지금 뜨면 그건 진짜 문제다.
  - 대신 **상시 가동 = 사용량 과금이 계속 붙는다.** 친구 테스트가 끝나면 Railway 대시보드에서
    서비스를 지우거나 App Sleeping을 켜 둘 것.
- **호스트 = 제일 좋은 컴퓨터**로. 시뮬+렌더+20Hz 직렬화가 전부 호스트 브라우저다.
  호스트 프레임 드랍은 전원 슬로모로 전파된다.
- **호스트는 탭을 앞에 유지**할 것. 탭을 숨기면 게임 전체가 "호스트 자리 비움"으로 정지한다
  (설계된 동작 — 브라우저가 숨김 탭 타이머를 1초로 클램프하기 때문에 정직하게 멈춘다).
- 클라 순간 끊김 = **그 판에서 제외** (재접속 없음 — v0.10 알려진 비용, 소지품은 그 자리에 안착).
- 호스트 이탈 = 방 소멸 (클라 전원 "호스트가 나갔다" 후 타이틀 복귀).

## 알려진 트레이드오프 (친구 테스트 관찰 항목 — D8·D16·D31)

- 4인이 병렬로 알을 집으면 **정전이 매우 일찍** 온다 (팀 합산 트리거는 계획 문서 권장 그대로).
  → 관찰: "정전이 너무 일찍 왔나? 밝은 구간(발각 게이지)이 충분히 노출됐나?"
- 4인의 발걸음 파동 + 랜턴 최대 4개 → 정전 어둠이 설계(1인 기준)보다 밝다.
  → 관찰: "정전이 시시했나?"
- NEED_EGGS=3 고정 × 4인 — 4번째의 상시 역할이 없다 (글러브·수레·미끼는 부수 역할).
  → 관찰: "4인일 때 심심한 사람이 나왔나?"
- 피드백은 **호스트 관점과 클라 관점을 분리해서** 수집할 것 (지연 체감이 비대칭이다).
